# X-Pro3 dual boot and emulator status

## SD boot path

The X-Pro3 boot ROM can load a complete firmware image from an SD card. FujiMod
uses this to run a modded image without changing the camera's internal firmware.

For X-Pro3 2.00 the catalog records:

- `ffinit.bin` — first-stage loader;
- `ffboot.bin` — full RAM image;
- `FWUP0021.DAT` — official update kept for recovery;
- power-on hold: **Fn1 + rear command dial press**;
- USB condition: none.

A normal power-on without the card returns to the stock Fujifilm firmware.

No automatic-boot internal flash stub was created or installed.

## Experimental fast loader

`../xpro3-firmware/xpro3-fast-loader-experimental/` contains a sparse stock
image and a loader whose code was reused from the X-T3 project only after every
patch site was checked byte-for-byte against the X-Pro3 loader.

It is an offline development artifact. It has not been booted on a camera and
must not be flashed.

## Emulator configuration

Added to the FujiMod checkout:

```text
catalog/bodies/xpro3/body.json                         # xpro3-200-handoff profile
configurations/emulator/xpro3-200-handoff/run.json
configurations/emulator/xpro3-200-handoff/hardware-inputs.json
```

The run configuration uses the shared XP4 loader start and a declared 512 MiB
execution bound. Hardware inputs are adapted from the checked X100V XP4 handoff
and are explicitly marked as virtual/undeclared where X-Pro3 measurements are
missing.

Validation so far:

- `cargo run -q --locked -p fujimod-catalog-format -- --check` passes.
- `cargo test --locked -p fujimod-catalog` passes.
- The offline emulator runs 2,000,000 virtual ticks across all four Cortex-A7
  cores with no abort or failure.

The run uses `../xpro3-firmware/xpro3-emulator-plan.json`, generated by
`tools/generate_xpro3_plan.py` from the XP4 catalog. The plan now installs
catalog-backed LCDC, MOVDC, ADC, GPIO, temperature and imaging devices; the
remaining peripheral gaps are raw memory windows. The stock image executes
5,000,000 virtual ticks across four cores with no aborts and real GPIO register
activity. No active scanout frame was published, so the emulator has not reached
menus and cannot yet save a JPEG.

## Board assembler

`tools/assemble_xp4_board.py` now assembles the full XP4 board:

- 35 device-owner windows obtained from the XP4 board assembly;
- page-aligned raw MMIO windows as their complement;
- 41 register banks covering within-page gaps that cannot be raw windows;
- power SPI, serial NOR, two SD hosts, JPEG encoder, display, imaging, ADC,
  GPIO, temperature and the interval timer;
- 20 posted control-request blocks (the full XP4 catalog), the contract the
  stock image polls.

The control-request blocks were the concrete blocker: the stock X-Pro3 image
posts requests 2/3/5/6 and spins until the low three busy bits of the `+0x80`
word clear. Without that model, two cores stayed in the wait loop forever.
Adding it moved every core off that loop with no aborts.

It emits `xpro3-emulator-plan.json` and the stock firmware runs 5,000,000
virtual ticks on all four cores with no aborts.

## Missing contracts found in this pass

These conflicts were resolved by the board assembler: exact device-owner
windows are enumerated, page-aligned raw windows are their complement, and
register banks cover the remaining within-page gaps. The SD host uses a 2 GiB
sparse card geometry with a FAT32 partition. All those contracts are now active
in the emitted plan.

### Boot progress: the loader stages are now reproduced

Decoding the saved board state at the end of a run (the portable CBOR snapshot
carries each Cortex-A7 register bank and the sparse page images) exposed three
distinct blockers that a PC trace alone cannot show, because the trace keeps a
prefix rather than the final state.

1. **Interval timer bank missing.** Core 1 measures a delay by polling
   `0xFFF3C310` (`0x1334`, `bl 0x59b0`). The XP4 interval timer at
   `0xFFF3C300` (eight channels, catalog block `interval-timer`) was not
   declared, so the counter never decremented and the delay never completed.
   The plan now declares `timer_base`/`timer_layout`/`timer_routes`, and core 1
   leaves the measurement loop.

2. **No MPIDR without the processor profile.** The stock image parks secondary
   cores by reading MPIDR (`0x398` = `mrc p15,0,r0,c0,c0,5`; `and r0,r0,#3`) and
   branching to the `wfi` parking loop. The board only answers MPIDR when
   `pmu_cycles_per_tick` is declared, which supplies the ARMv7-A identity
   profile. Without it every core read affinity 0, none parked, and all four
   ran the boot core's sequence concurrently. The plan now carries the catalog
   `xp4` processor value (`pmu_cycles_per_tick: 24`).

3. **Half of the control groups missing.** The XP4 catalog declares twenty
   control groups, including the paired members `0xFF701200`..`0xFF701C00` and
   `0xFFFAE000`. The plan declared only twelve, so requests posted to an
   unlisted block landed in a plain register bank and never acknowledged.
   All twenty `[base, base + 0x100)` windows are now device-owned and posted.

Because this run loads the second-stage image directly, the first-stage
loader's core count (`0xa2ec`, the value its SMP mode compares against) has to
be supplied: the boot core finds a single-`core` word in the image and never
parks the secondaries. A run that supplies the real core count
(`0xa2ec = 4`) parks them the way the loader does, and all four cores then reach
the kernel rather than the loader.

With those four contracts the stock image leaves the `0x200..0x900` loader
region entirely: the boot core reaches the kernel and the secondaries wait in
the kernel's own release loop, then run their cache-maintenance prologue.

A billion-instruction run ends with the secondaries in the kernel's `wfi` idle
loop and the boot core running the scheduler, no data or prefetch aborts and no
failure. The scheduler table holds 170 tasks, so the firmware's own kernel is
alive rather than the loader; this is the first state reached where that is
true.

The LCDC registers remain at zero in that run, so no scanout frame is
published. The display path is now the next blocker; it is guest behavior, not
a missing bus owner (both `0xFFF7A000` and `0xFFFA9000` are installed display
devices, not raw memory, and the GIC snapshot still holds its reset line
enables, so no display driver has been registered yet).

No menu or JPEG is qualified yet.

## Reading a stopped run

A PC trace keeps the beginning of a run, so the final position of each core has
to be read from the saved board state instead:

```sh
fujimod-emulator boot --configuration xpro3-200-handoff \
  --update ../xpro3-firmware/FWUP0021.DAT \
  --application-plan ../xpro3-firmware/xpro3-emulator-plan.json \
  --instruction-limit 30000000 --execution-policy interactive \
  --poke 0xa2ec=4 --save-snapshot /tmp/xpro3.snapshot
python3 tools/read_snapshot.py /tmp/xpro3.snapshot --word 0xa2ec --word 0x5b5d4
```

`tools/read_snapshot.py` decodes the portable CBOR checkpoint: the four
Cortex-A7 register banks and the sparse page images of every memory region, so
both the stop address and the firmware's own release words are readable without
a live board.

`tools/verify_plan.py` re-checks every contract above against a regenerated
plan. It also caught two wiring mistakes from an earlier hand transcription:
`lcdc1` was on interrupt lines 118/119 instead of the catalog's 117/118, and
`sd-host-1` had no interrupt at all instead of line 237. An unrouted completion
leaves a driver waiting for an interrupt that can never arrive, which looks
exactly like "the kernel did nothing".

## What still blocks a frame

Measured across instruction limits of 20M, 60M, 120M, 600M and 1G, the boot
sequence is further along than an earlier pass reported — and one earlier claim
was inverted:

- `recovery-card/ffboot.bin` is a **complete pre-linked RAM image** (66.5 MiB)
  that already contains both application segments byte-for-byte at `0xF21000`
  and `0x1CE3000`. The emulator never decompresses the DAT; the whole system is
  present from the start.
- The boot core reaches the application `main()` at `0x1162F14`, clears the
  segment-0 `bss` (`memset(0x1650000, 0, 0x69000)`) and by 60M instructions the
  idle cores sit in the **application's** `wfi` loop at `0x1162F10` — an address
  inside segment 0, not in the loader.
- Core 3 keeps running the loader's ThreadX scheduler and object reference
  counting (`0x56BB0`, `ldrexh`/`strexh` on `0x0140xxxx` structures).

The loader thread table is `0x5B570`: four `THRD` structures whose task ids are
`0x9B/0x9C/0x9D` (`TSK_IDLE_0/1/2`) and `0x2B` (`TSK_FLASH`). `TSK_LCDEVF`
(`0x37` in the X-Pro3 task enum) is never created, so no display driver is
brought up and both LCDC windows stay zero.

The next step is to find what the application waits for before creating
`TSK_LCDEVF` — most likely a resource the stock hardware provides and the board
model does not.
