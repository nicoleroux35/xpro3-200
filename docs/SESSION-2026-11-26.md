# X-Pro3 2.00 emulator — session 2026-11-26 (findings)

> **Superseded in part.** Three conclusions below did not survive further
> measurement. Read [`CORRECTIONS-2026-11-27.md`](CORRECTIONS-2026-11-27.md)
> first:
>
> - the storage stop was a defect in the **declared DMA routes** (`32..47`
>   instead of `207..222`), not firmware dispatch design — §5, §8 and §10
>   item 1 below are wrong;
> - `0x1090C0C` is a three-mode transfer primitive, not a thread spawner, and
>   `FUN_010916A4` is not a function — §5 and §10;
> - the application tasks are **registered but never created** by the code
>   that runs, which is the actual remaining blocker.
>
> This file is kept unchanged as the record of that session.

Scope: `fujimod-emulator boot --configuration xpro3-200-handoff`, i.e. the
application profile. No camera, no SD card, no firmware written.

## 1. The emulator itself is healthy

```
fujimod-emulator boot --configuration xpro3-200-handoff \
  --update FWUP0021.DAT \
  --application-plan xpro3-emulator-plan.json \
  --instruction-limit 400000000 --execution-policy interactive \
  --poke 0xa2ec=4 --save-snapshot xp3-snap.bin
```

| Measure | Value |
| --- | --- |
| engine | unicorn |
| instructions | 400 000 000 (`[23.5M, 9.1M, 9.2M, 358M]` per core) |
| data aborts / prefetch aborts / undefined | **0 / 0 / 0** |
| `state.failure` | `null` |
| `--screenshot` | `no active scanout published a frame` |

Reproducible: two runs of the same configuration produce the same milestone
order and the same stopped PCs. The emulator is a trustworthy analysis bench
for this firmware; it does not yet reach the GUI.

## 2. Boot chain actually executed (milestones)

Labels were added to a **copy** of the plan (`definition.labels`), never to the
committed one. Instruction counter at first entry of each address:

```
  3 324 610  main()                            0x1162F14
 24 088 785  task registration (1/11)          0x114F798
 24 233 595  tx_thread_create wrapper          0x4C1E0
 24 260 028  tx_thread_create                  0x4C04C
 24 329 675  TSK_ROOT body                     0x1163500
 24 369 752  task start                        0x1150210
 24 405 310  12 successive init functions      0x1152B30 .. 0x1152C18
 34 767 064  storage init                      0x1163744
 34 767 065  configuration read                0x113A7BC
 37 397 276  NOR read through 0xFFFD80xx       0x1093410
 37 397 417  transfer-engine wait (0x400)      0x109099C   <-- last thing reached
```

Everything after that is never entered, `0x1163754` included. Core 0 then sits
at `0x01162F10` (`wfi`).

## 3. Task creation is not the problem — dispatch is

`0x1150210` (start task) is called **169 times** and returns **0 (success)**
every time; `0x4BE9C` (registry insert) also returns 0 every time. The registry
at `0x7A944[id-1]` therefore holds all 167 descriptors, which is what the
snapshot shows.

What is missing is the second half: `0x114F798` — the function that actually
calls `tx_thread_create` — is entered only **11 times**. Those 11 are the
loader-owned threads:

| address | id | name | state |
| --- | --- | --- | --- |
| `0x068CC4` | `0x2B` | `timer` | 3 = SUSPENDED, wait 4 (event), mask `0x2B` |
| `0x06E8A4`..`0x06EDE4` | `0x71`..`0x75` | `execcpu` ×5 | 3 = SUSPENDED, wait 4, mask own id |
| `0x071FC4`..`0x0723B4` | `0x9B`..`0x9E` | `idle0..3` | 0..3, wait 2 (ready) |
| `0x072504` | `0x9F` | `root` | 0, wait 4, subtype 8 (queue) |

No `THRD` exists for any of the 165 application task ids (`0x01..0x9A`,
including `TSK_UILIB` `0x36` and `TSK_LCDEVF` `0x37`).

## 4. Why the storage path blocks

`0x10907AC` is the transfer submitter. After the NOR command it checks the
engine's completion slot:

```
0x109089C  cmp r0, #0
0x10908A4  cmp sb, #0            ; sb = 4th argument, async request
0x10908A8  beq 0x10908C0        ; synchronous -> poll instead
0x10908AC  ldr r3, [0x16A2D0C+0x24]   ; completion callback / token
0x10908B8  cmn r3, #1
0x10908BC  bne 0x109099C        ; armed -> wait for it
0x109099C  tx_event_flags_get(flags=0x400, timeout=-1)   ; never returns
```

Measured state at the block: `[0x16A2D24] = 0x00010000` (armed, not -1), so the
wait is entered. The poster of `0x400` is `0x1090BEC`:

```
0x1090BEC  ldr r0, [0x16A2D0C+0x24]
0x1090C04  bl  0x11500F4        ; event set wrapper
```

`0x1090BEC` is **never entered** in any run. The only other events actually
posted in the whole run are `flags=0xFFFFFBFF` to task `0x9F` from
`0x4A94C` (i.e. "clear 0x400"), the mirror of the handshake.

## 4 bis. Which thread-creation sites actually run

Of the 90 call sites of `0x114F798` (the function that reaches
`tx_thread_create`), exactly **7** are reached:

| instruction | site | what it creates |
| --- | ---: | --- |
| 24 088 784 | `0x1162F98` | `root` (`0x9F`) |
| 24 330 947 | `0x1163554` | `idle0` (`0x9B`) |
| 24 341 579 | `0x1163580` | `idle1` (`0x9C`) |
| 24 351 880 | `0x11635AC` | `idle2` (`0x9D`) |
| 24 361 332 | `0x11635D8` | `idle3` (`0x9E`) |
| 34 572 161 | `0x1143CA0` | a loader-side helper |
| 34 690 767 | `0x11359EC` | a loader-side helper |

`TSK_ROOT` already registers 4 idles before its 167-task start loop, so those
are not "the app tasks". The other 83 sites belong to subsystem init code that
the storage block prevents from ever running.

## 5. Root cause (proven by decompilation)

Decompiled with Ghidra 12.2 (`ARM:LE:32:v7`, **not** the Cortex/Thumb default,
which decodes this image wrongly), sources archived in
`reports/decompile/`.

The whole transfer path is the same function family, and its structure is:

```c
// 0x10907AC — submit one transfer
if (engine_busy_ok(...)) {
    iVar1 = current_task_id();                 // 0x114FC44
    if (iVar1 != 0 && async_flag != 0) {       // async_flag = param_4
        cb = 0x1090BEC;                        // posts 0x400
        DAT_016a2d30 = iVar1;                  // = 0x9F (root)
        clear_event(0xFFFFFBFF);               // 0x11501BC
    } else {
        cb = 0;
        DAT_016a2d30 = 0xFFFFFFFF;
    }
    enqueue(engine, &cb);                      // 0x10973DC
    ...
    if (async_flag == 0 || DAT_016a2d30 == -1)
        poll_until_done();                     // 0x109808C loop
    else
        wait_event(0x400, INFINITE);           // 0x1150004  <-- the stop
    finish(0x1097B40, 0x1096FD4);
}
```

Measured: `DAT_016a2d30 = 0x9F` and the callback is set, so the wait branch is
taken. The poster is `0x1090BEC` = `set_event(DAT_016a2d30, 0x400)`.

**Nothing ever posts it.** The only producer that could is the progress
callback registered by `0x1090AFC`:

```c
// 0x1090AFC — register the progress callback
iVar1 = current_task_id();
if (iVar1 == 0 || param_1 != 1) {      // <-- gated on param_1 == 1
    DAT_016a2d14 = 0;
    return 0;
}
subscribe(DAT_016a2d18, 0x1090E68, &DAT_016a2d14);
```

and `0x1090E68` is the code that actually sets `0x100`:

```c
// 0x1090E68 — progress callback
if (local_13 & 0x40) {
    if (DAT_016a2d38 == 1) { ... set_event(cas_owner, 0x100); }
    else if (DAT_016a2d2c != -1 &&
             compare_and_swap(&DAT_016a2d2c, DAT_016a2d2c, -1) != 0)
        set_event(iVar1, 0x100);   // 0x11500F4
}
```

`param_1` is the 3rd argument of `0x1090F70` / `0x109110B4`, propagated as
`param_4` of `0x10907AC`. Every caller measured passes **1** at one site only:

| caller | call | flag |
| --- | --- | --- |
| `FUN_010916A4` @ `0x10918A4` | `FUN_01090F70(addr, len, ctx)` | `ctx` from `[r11-0x28]` |
| `FUN_010916A4` @ `0x1091840` | `FUN_010910B4(addr, dst, ctx, 1, n)` | **1 (literal)** |
| `FUN_010909E4` @ `0x1090A40` | `FUN_010907AC(.., .., .., ctx, .., 1)` | **1 (literal)** |
| `FUN_010910B4` @ `0x1091178` | `FUN_010907AC(.., .., .., ctx, .., 0)` | 0 → synchronous |
| `FUN_010913D8` @ `0x10914F8` | `FUN_010907AC(.., .., .., ctx, .., sb)` | from caller |

So: when a subsystem issues a transfer that needs the progress callback, it
passes `1`; the callback is registered; `0x1090C0C` then waits for `0x100` —
which is posted by `0x1090BA8`, itself only invoked from the **interrupt
service thread** it spawns via `FUN_0108B550`/`FUN_0108B118`, and that path
requires `current_task_id() != 0` **twice**.

Measured in every run: the four sites that would register the progress callback
(`0x1090FAC`, `0x10910E8`, `0x10911B0`, `0x10911EC` for `0x1090AFC`, plus
`0x1090AF8`'s gate) are **never reached**, and `0x1090BEC`/`0x1090BA8` are
**never entered**. The only transfer that does start is the synchronous
one-shot NOR read at `0x10914F8` (`sb` from its own caller), which completes and
then blocks on `0x400` because its caller passed an async flag that its
completion path cannot serve.

In short: **the firmware's storage engine is designed to be driven by a
secondary (EXEC CPU) thread, and in this configuration that driver never runs.**
The five `execcpu` threads exist but stay `SUSPENDED` on their own event masks,
cores 1 and 2 sit in `wfi`, and core 3 is parked by the loader. Confirmed at
800 M instructions: identical state, no further milestone.

The original commentary for this section, kept for the record:

The transfer engine keeps its state at `0x16A2D0C` (`magic 0x77666555` at
`+0x00`). The async branch of `0x10907AC` (`sb != 0`, i.e. a DMA-style request)
does this before waiting:

```
0x1090968  r3 = 0x1090BEC                 ; completion callback
0x1090970  str r3, [fp, #-0x3c]
0x1090974  r3 = 0x16A2D0C
0x109097C  str sl, [r3, #0x24]            ; sl = current task id  -> 0x16A2D30 = 0x9F
0x1090980  r0 = ~0x400
0x1090984  bl 0x11501BC                   ; clear flag 0x400
0x1090868  bl 0x10973DC                   ; enqueue callback + context, engine queue at 0x16A2F28
```

Measured at the stop: `[0x16A2D30] = 0x9F` (the waiter is `root`) and the queue
entry `0x143893C` exists with its state byte `+2 == 2`. So the callback is
registered and the context is correct.

`0x1090BEC` — the only poster of `0x400`, targeting task `0x9F` — **is never
entered**. Something must dequeue `0x16A2F28` and call it; that consumer never
runs in this configuration.

The related registration function is `0x1090AFC` (`bl 0x114FC44` = "current
task id", then `cmd id == 1` gates registering `0x1090E68`, which posts `0x100`
to `+0x28`'s owner). It has four call sites — `0x1090FAC`, `0x10910E8`,
`0x10911B0`, `0x10911EC` — and **none of them is ever reached** in the run
labelled with all four. Only `0x109099C` is reached.

In this run the five `execcpu` threads exist but are **all still SUSPENDED**
waiting on their own event masks, and cores 1/2 sit in `wfi` with core 3 parked
in the loader. Nobody drains the engine queue, so `0x400` is never posted and
the `timeout=-1` wait is final.

So the blocker is **firmware dispatch design**, not a missing device model.
That also explains why the X-T3 reaches REC in this same emulator: its profile
was built from a real JIG RAM capture (see `catalog/bodies/xt3/body.json`,
`xt3-discovery`), while `xpro3-200-handoff` declares virtual inputs only
(`"...physical X-Pro3 ... unmeasured"` in `hardware-inputs.json`).

## 6. The decisive experiment: polling instead of the event-flag wait

Forcing the synchronous branch (`0x10908A4` `cmp sb,#0` → `mov r0,#0`, i.e.
`beq 0x10908C0` always taken) makes the run **pass the stop**:

```
45 M   after the wait label    0x109099C -> 0x10908C0 polling loop -> 0x1093508
        -> storage transfer completes -> returns into TSK_ROOT
        -> then: fujimod-emulator: Unsupported power SPI write register17
```

Declaring the power-SPI command output (`register 17 = 4096`) then gets past
that, and the run continues into the imaging path. Two conclusions:

1. **The storage transfer itself works.** The block is exclusively the
   completion event (`0x400`), which needs the engine's service thread.
2. The two model gaps (`power_spi` register 17 write, fixed-destination DMA)
   were the *next* two refusals and are now understood.

A run with `--discovery` (needed for the transmit receiver) reaches
600 M instructions with `failure: null` and no model refusal. Cores 0 and 3 are
busy, 1 and 2 idle — different from the blocked profile. Snapshots are refused
in discovery mode, so this run has to be observed with labels only.

## 7. Why the `open` pipeline cannot help yet

`fujimod-emulator open --firmware xpro3-200 --boot stock` fails before booting:
`crates/emulator-boot/src/lib.rs` requires, for the open path, both

- `firmware.boot_rom` — **null** in `catalog/progress/xpro3/2.00`, and
- `firmware.installation` + `generated_facts.observation`
  (`ui_mode`, `system_mode`, `readiness`, `scanout`) — **absent** from
  `catalog/firmware/xpro3/2.00/firmware.json`, while X-T3 5.11 has
  `installation` with entry labels and image sections.

So reaching REC through the official pipeline needs catalog facts that only a
real RAM/flash capture (JIG `ff80`) can produce. That is the same conclusion as
the X-T3 precedent: `catalog/bodies/xt3/body.json` says its profile came from a
guarded JIG capture, and X-T3 is the only XP4 body marked "Boots to the
shooting screen" in the catalog.

## 8. GIC lines actually enabled on X-Pro3

Snapshot `gic.enabled[0]` = `[0..15, 63, 64, 207]`. The plan's
`storage_irq = 37` and `storage_dma_routes = [32..47]` are therefore **not**
armed by this firmware; the storage path is polled plus one worker thread.
Changing those numbers will not unblock anything.

## 9. What the earlier diagnostic patches showed (and did not show)

| Patch | Result |
| --- | --- |
| `0x10909A8` `bl` → `mov r0,#0` (claim the wait succeeded) | passes `0x10908E8`, then hits `Unsupported power SPI write register17` |
| `0x10909A8` done, plus `power_spi_command_output = {register:17, value:4096}` | passes, then hits `XP4 fixed-destination DMA is not modeled` |
| `0x1090A28` `mov r3,#1` → `#0` (force synchronous) | **no effect**: the real submit site is `0x10914F8`, not `0x1090A40` |

Also measured with a 800 M instruction run (13 min wall): the stop is identical.
Cores end in `wfi` (`0x01162F10`, core 3 in the loader), the `THRD` set is the
same 11 threads, no milestone appears after `0x109099C`. The block is terminal
in this configuration, not a slow path.

Two model gaps to close later, in this order: `power_serial` register 17 as a
writable output, then fixed-destination DMA in `emulator-xp4-storage`
(`storage.rs`, `c.regs[0x20/4] & 4` with `receiver.is_none()`).

## 10. Next steps, ranked

1. **Make the engine's service thread exist** (the real unlock). `0x1090C0C`
   spawns it through `FUN_0108B118`/`FUN_0108B550` with callback `0x1090BA8`
   (posts `0x100`), and only runs when `current_task_id() != 0` **and**
   `param_2 != 0`. Then `0x1090E68` (progress callback) can post `0x100` and
   `0x1090BEC` can post `0x400`. Finding why that path is never entered — the
   four callers of `0x1090C0C` are `0x1091000`, `0x1091098`, `0x10911A0`,
   `0x1091254`, all unreached — is the single remaining question for a stock
   X-Pro3 boot.
2. **Catalog facts for X-Pro3** (`boot_rom`, `installation`,
   `generated_facts.observation`) so the `open` pipeline can run at all. Only a
   real capture on the body can produce them (`ff80` bulk + flash).
3. **Close the two model gaps** now proven necessary:
   `power_serial` register 17 as a writable declared output, and
   fixed-destination DMA in `emulator-xp4-storage`.
4. Then scanout, then `sd-boot-v1` and the dual-boot question.

## 11. How to reproduce this session

Two helper scripts were added, both dependency-free:

```bash
# 1. label the plan (passive observation points only)
tools/add_labels.py ../xpro3-firmware/xpro3-emulator-plan.json /tmp/xp3-plan.json --boot-chain

# 2. build the diagnostic plan + patch that get past the engine stop
tools/make_diagnostic_plan.py ../xpro3-firmware/xpro3-emulator-plan.json \
    /tmp/xp3-diag-plan.json --patch-out /tmp/xp3-diag-patch.toml

# 3. run it (note --discovery: it is a CLI flag, not a plan key)
./target/debug/fujimod-emulator boot --configuration xpro3-200-handoff \
  --update ../xpro3-firmware/FWUP0021.DAT \
  --application-plan /tmp/xp3-diag-plan.json \
  --instruction-limit 80000000 --execution-policy interactive --discovery \
  --poke 0xa2ec=4 --patch /tmp/xp3-diag-patch.toml

# 4. read milestones, calls (with arguments and results) and memory
tools/add_labels.py ... ; python3 tools/read_snapshot.py /tmp/xp3-snap.bin \
  --word 0x16A2D24
```

Snapshots are refused in discovery mode; use plain label runs
(`--save-snapshot`) when you need to read memory.

Decompilation: import with `-processor ARM:LE:32:v7` (**not**
`ARM:LE:32:Cortex`, which defaults to Thumb and mis-decodes this image), then
run `reports/decompile/Xpro3Decompile3.java`, `Xpro3Callers.java`,
`Xpro3Entries.java`, `Xpro3Storage.java` with `analyzeHeadless -postScript`.
Outputs are archived next to the scripts in `reports/decompile/`.
