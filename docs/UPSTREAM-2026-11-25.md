## Facts verified locally against our own firmware file

- `FWUP0021.DAT` container `os_type = 6`, model code `00055711`, version 2.00,
  plaintext header 0x274 bytes, payload XOR 0xFF.
- Header checksum reproduces exactly:
  `0x20C = 0xFFFFFFFF − Σ(de-inverted payload[0:0x2FC0020])` → `0xc54bab2e`.
- **No NIST P-256 public key and no signature OIDs** anywhere in the file
  (`find-pub-key.py` finds no valid point; the P-256, ECDSA-SHA256, RSA and
  SHA256-RSA OIDs, `BEGIN PUBLIC KEY`, `prime256v1` all occur 0 times). This
  matches the cross-model finding that the stock 32-bit bodies carry no
  signature check on the update path.

## Still missing (the short list)

1. **A ThreadX-aware X-Pro3 disassembly**: the boot image runs a ThreadX kernel
   with 152 named tasks; the `TSK_*` table exists for X100V/X-T3 but not for
   X-Pro3 2.00.
2. **An X-Pro3 `fffw` port** (`ffun/ports/xpro3/0200/`): task/struct/enum
   headers and an ELF export for Ghidra.
3. **X-Pro3 function map** beyond the five addresses given by
   `CROSS-MODEL-COMPARISON.md` (`FUN_01d425f0`, `FUN_01f882a8`, `FUN_01f8c9d0`).
4. **A FujiMod X-Pro3 mod target** — `catalog/progress/xpro3` lists `mod-target`,
   `mod-build`, `mod-effect` and all ~60 mod rows as `not-run`.
5. **An emulator screen**: `catalog/progress/xpro3` marks `rec`, `emulator-screen`
   and `menu` as `not-run`; our own runs reach the kernel but publish no LCDC
   frame.
6. **Physical inputs for X-Pro3**: `catalog/progress/xpro3` marks `controls` and
   `settings-layout` as `stale`/`not-run`; our plan still borrows the X100V
   ADC/GPIO fixture.
7. **Boot ROM**: `boot_rom` is `null` in `catalog/progress/xpro3` (`boot-rom:
   not-run`); the SD boot path is documented but the ROM itself is not captured.
8. **A published X-Pro3 feature patch** (film sims, 4K, etc.): none exists; the
   X-Pro1 recipe and the X-T3/X-T30 II payloads are the only worked examples.
